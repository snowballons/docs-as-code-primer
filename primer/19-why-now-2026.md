# Why now (2026)

Docs-as-code discipline has existed for years. Three converging trends make it urgent now.

## 1. AI agents depend on structure

AI coding assistants consume documentation at inference and training time. They cannot infer structure from unstructured content. Teams whose docs are accurate, well-structured, and machine-readable see measurably better AI-assisted development outcomes.

| Content type | Agent value | Without structure |
|---|---|---|
| Architecture overview | Agent understands system boundaries before writing code | Agent invents APIs or assumptions |
| API contracts (OpenAPI) | Agent generates correct calls and error handling | Agent guesses endpoints and formats |
| Runbooks | Agent can diagnose and suggest remediation | Agent guesses — may hallucinate dangerous commands |
| Glossary | Agent uses consistent terminology | Agent introduces naming drift |

Teams that defer docs-as-code until "after launch" are making their codebases less accessible to the AI tools their engineers will rely on.

## 2. LLMs raised the bar for user docs

Users now expect documentation that answers their question in one sentence, with a working example. The old pattern — "read the manual, find the endpoint, try it" — fails against an LLM that can summarize, compare, and generate code from a well-structured API reference.

The winning pattern: structured docs that LLMs can accurately retrieve from, combined with a curated user experience for direct readers.

## 3. Documentation debt compounds faster

AI coding assistants accelerate code production. More code per sprint means more surface area to document. Without docs-as-code discipline:

- Code output grows 2–3x (AI-assisted)
- Documentation capacity stays flat
- Knowledge gap widens every sprint

The teams that will sustain velocity are those where doc updates are as automated and habitual as code reviews.

## Maturity model

| Level | Characteristics | You're here when |
|-------|----------------|-------------------|
| 0 — Chaos | Docs exist in Slack, Confluence, and READMEs from 2022. No one knows what's current. | You can't find the architecture overview in 5 minutes |
| 1 — Scaffold | Git-based structure exists. PRs include doc changes some of the time. Links are checked. | You use this kit's scaffold and pass link checks |
| 2 — Discipline | Phases 0–6 are practiced. ADRs are written before major decisions. Runbooks live in Git and are tested. Internal and user streams are separated. | Every PR considers docs. New engineers get productive in one day. |
| 3 — Platform | Dual pipelines publish internal and user docs independently. MCP or agent hooks expose docs to tools. Doc health is reviewed monthly. | Documentation is a first-class artifact, as automated as tests. |

## What this means for your team

If you're starting fresh: scaffold first, then fill Phase 0–2 honestly before writing code. The kit exists to make that path copy-pasteable.

If you're retrofitting: pick one phase, make it habitual, then expand. Level 1 is achievable in a week. Level 2 in a quarter. Level 3 is aspirational and may not fit every team's size.
